# supabase/

Single source of truth for the database schema. Shared by the portal and the mobile app (`../impulsa360`).

## Layout

- `migrations/`: versioned migrations. First file is the prod baseline dump.
- `legacy/`: pre-baseline history. Reference only, never replayed.
- `config.toml`: CLI config as generated by `supabase init`. No secrets.

## Projects

| Env | Name |
|---|---|
| prod | yoloIntegrat360 |
| dev | yoloIntegrat360-dev |

## Commands

```
supabase migration new <name>                     # create file (never name it by hand)
supabase db push --dry-run --db-url "$DEV_DB_URL" # list pending migrations
supabase db push --db-url "$DEV_DB_URL"           # apply pending migrations
supabase migration list --db-url "$DEV_DB_URL"    # local vs remote history
```

Same commands with `$PROD_DB_URL` for prod. Connection strings live in `.env` (git-ignored); use the Session pooler URL.

## Rules

- Never edit an applied migration. Add a new one.
- Never change schema in the SQL Editor. If unavoidable, capture it as a migration the same day.
- Prod pushes need explicit approval.
- Deploy DB before apps. Keep changes backward compatible with every mobile build in the field.
- Expand/contract: add the new column or function, ship both apps, drop the old one only after the oldest supported build stops using it.
- Enable RLS on every table in `public`. Keep `security definer` functions to a minimum, with `set search_path = ''`.
- No data in migrations except reference data.
